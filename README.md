# 销售明细智能问答（Text-to-SQL 最小闭环）

用自然语言问销售数据，模型生成 SQL，本地数据库执行，再把结果翻译成中文回答。

例如问一句「哪个品牌的销售额最高？」，系统自己写出 `SELECT brand, SUM(amount) ... ORDER BY ... LIMIT 1`，查库后回答「木野，113,501.02 元」。

> 数据全部由脚本随机生成的虚构销售明细（200 行，固定随机种子），品牌、门店代码均为虚构，不含任何真实业务数据或个人信息。



---

## 演示输出（本机真实运行结果）

```
问题：哪个品牌的销售额最高？
SQL ：SELECT brand, SUM(amount) AS total_amount FROM sales_detail
      GROUP BY brand ORDER BY total_amount DESC LIMIT 1
结果：[{"brand": "木野", "total_amount": 113501.02}]
回答：销售额最高的品牌是木野，其销售额为 113,501.02 元。
```

```
问题：退货冲销的记录有多少条、合计金额是多少？
SQL ：SELECT COUNT(*) AS 退货记录数, SUM(amount) AS 合计金额
      FROM sales_detail WHERE sales_type = '退货冲销'
回答：退货冲销记录共有 24 条，合计金额为 -19,807.74 元。
```

```
问题：按会员等级统计销售额？
回答：sales_detail 表中没有「会员等级」字段，无法按会员等级统计销售额。
```

第三条是刻意设计的：表里没有这个字段，模型选择明确说明做不到，而不是编一个字段让 SQL 报错。

---

## 技术链路

```
自然语言问题
  → 把表结构（字段名 / 类型 / 中文含义）注入 system prompt
  → 模型只输出一条 SQL
  → 本地安全校验（只允许 SELECT）
  → SQLite 执行；若报错，把错误信息回传模型自动改一次
  → 模型把查询结果组织成中文回答
```

关键点：**模型一个数都没算过**。122,468.94 这类数字是 SQLite 算的，模型只负责把中文翻译成 SQL、再把结果说成人话。所有 Agent 的底层分工都是这样——模型负责生成和决策，代码负责执行和校验。

---

## 三个工程细节（面试重点）

1. **schema 注入**：把字段名、类型、中文含义写进 prompt，模型才知道有哪些列可用。这是所有 Text-to-SQL 的地基，也来自真实业务里「给字段写中文 COMMENT」的习惯。
2. **SELECT 白名单**：模型返回的文本本质不可信，执行前统一校验，只放行 `SELECT`，拦住 `DROP / DELETE / UPDATE`。这是工程可控性，不是工具熟练度。
3. **失败回退**：SQL 执行报错时，把错误信息回给模型让它改一次。这是「观察 → 纠错」循环的最小形态。

零第三方依赖：只用 Python 标准库（`urllib` + `sqlite3`），Python 3.8+ 直接跑，不用 `pip install`。模型走 DeepSeek 的 OpenAI 兼容接口。

## 验证记录与发现

手工跑了 8 个有代表性的问题，覆盖聚合、多条件、分组排序、退货口径、模糊口径、不存在的字段和月份。发现的失败模式比「跑通」本身更值得记：

| 问题         | 模型表现                                 | 判断                                   |
| ---------- | ------------------------------------ | ------------------------------------ |
| 各渠道退货率     | 用 `ABS(SUM(退货金额)) / SUM(amount)` 作分母 | 公式看着专业，但分母是净销售额（已扣退货），口径偏高；应先定义清分子分母 |
| 各品牌平均客单价   | 用 `SUM(amount)/COUNT(*)`             | 表里没有订单号，它自己把客单价定义成「行均金额」，能算但不是严格客单价  |
| 按会员等级统计销售额 | 明确回答「表里没有这个字段」                       | 正确行为——不硬编字段、不编造答案                    |
| 每个月的销售额    | 只返回实际存在的 2026-07 一行                  | 正确行为——没有的月份不编造                       |

结论：模型写 SQL 的能力已经不是瓶颈，风险集中在**口径**——退货率、客单价、销量这类「数字或高或低都能说圆」的地方，出题前必须先把统计口径写死。系统性量化评测（20–30 题算准确率）尚未开展，这是下一步。

## 已知边界

- 这是单轮闭环，不是多轮自主 Agent：模型没有权力决定「下一步查什么」。
- 数据库是 SQLite 内存库、数据是虚构的，不是生产系统。
- 只做自然语言到 SQL 的查询入口，没有接入前端，也没有真实服务部署。
